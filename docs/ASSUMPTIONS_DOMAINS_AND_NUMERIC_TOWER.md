# FrankenSymPy assumptions, domains, and numeric tower

**Status:** normative architecture contract  
**Scope:** logical contexts, domain inference/coercion, exact arithmetic, algebraic numbers, transcendental constants, floating-point compatibility, certified numerics

## 1. Prime directive

Symbolic correctness depends as much on the domain and assumptions as on the expression syntax. `sqrt(x**2) = x` is not universally valid; polynomial factorization depends on the coefficient domain; branch-sensitive functions change meaning across real and complex domains; numerical evidence is not exact identity.

FrankenSymPy therefore makes domain, assumptions context, branch policy, and evidence class explicit inputs to every semantic operation.

## 2. Four distinct concepts

The implementation must never conflate:

1. **Sort/kind:** what category of value an expression denotes, such as scalar, Boolean, set, matrix, tensor, distribution, or unevaluated object.
2. **Algebraic domain:** the coefficient/value universe and its operations, such as `ZZ`, `QQ`, `GF(p)`, `QQ(α)`, `RR_ball`, a polynomial ring, a quotient ring, or a matrix ring.
3. **Assumptions context:** predicates known, denied, or unknown for symbols and expressions within an immutable reasoning snapshot.
4. **Compatibility facts:** profile-visible class/instance assumptions and cache behavior that may not coincide one-to-one with the kernel's logical representation.

Each receives a distinct typed ID.

## 3. Assumptions truth model

The base query result is four-way at the kernel boundary:

```text
EntailedTrue(proof)
EntailedFalse(proof)
Unknown(reason)
Contradictory(witness)
```

The compatibility shell maps these results to the profiled `True`/`False`/`None` behavior or profiled exception behavior. Contradiction must not silently collapse to `None` in native mode, though the shell may reproduce upstream behavior where required.

### 3.1 Why four-way internally

A three-valued user API is insufficient for diagnostics and proof search. “Unknown because no applicable rule exists,” “unknown because the budget expired,” and “both a predicate and its negation follow from inconsistent facts” require different handling. Native mode preserves the distinction; compatibility mode reproduces the selected profile.

## 4. Immutable assumptions contexts

An `AssumptionsContext` contains:

```text
AssumptionsContext
├── context_id
├── parent_context_id, optional
├── explicit facts
├── retractions/shadowing entries
├── predicate registry version
├── inference rule registry version
├── domain declarations
├── branch policy
├── consistency policy
├── opaque hook facts with provenance
└── content digest
```

Contexts are immutable. Adding facts creates a child context. This allows:

- deterministic replay;
- safe concurrent derivations;
- exact cache keys;
- branch-per-agent reasoning;
- proof edges that name their logical universe;
- efficient structural sharing.

A mutable Python `assuming(...)` or equivalent context manager is implemented as shell-local context selection, not mutation of a global kernel database.

## 5. Fact representation

Facts are typed predicates over term IDs:

```text
PredicateApplication
├── predicate_id
├── ordered term_ids
├── polarity
├── source
├── evidence class
└── scope
```

Sources include:

- symbol constructor assumptions;
- class defaults;
- domain membership;
- trusted kernel theorems;
- verified derivations;
- user assertions;
- compatibility hooks such as `_eval_is_*`;
- imported proof bundles;
- heuristic observations, which cannot discharge exact obligations.

A fact's provenance determines what it may justify. A user assertion may govern a requested derivation; a heuristic observation may guide search but not prove a theorem.

## 6. Inference engine

The inference system is stratified.

### 6.1 Tier 0: definitional facts

Facts inherent in a term/domain representation, such as:

- an `Integer` term belongs to `ZZ`, `QQ`, and algebraic/real/complex supersets;
- a matrix dimension descriptor is fixed;
- a finite-field element has characteristic `p`;
- a positive integer is nonzero and real.

These are generated by small trusted code and can carry kernel-level evidence.

### 6.2 Tier 1: Horn-style predicate closure

Versioned rules derive ordinary implications with termination controls, e.g.:

```text
integer(x) -> rational(x)
rational(x) -> real(x)
positive(x) -> nonnegative(x)
positive(x) -> nonzero(x)
```

The rule engine records proof parents and detects cycles without assuming cyclic support is evidence.

### 6.3 Tier 2: structural handlers

Operator-specific reasoning handles facts such as signs of products, parity of sums, matrix properties, set membership, and function ranges. Every handler declares:

- accepted domains and sorts;
- exact side conditions;
- termination measure;
- evidence class;
- dependencies on branch policy;
- compatibility-hook interaction.

### 6.4 Tier 3: solver-backed obligations

Some queries reduce to polynomial inequalities, satisfiability, quantifier elimination, linear arithmetic, or certified numerical separation. These are budgeted subcomputations that return certificates or `Unknown`; they cannot silently time out into false.

### 6.5 Tier 4: Python hooks

Profile-defined `_eval_is_*` and predicate handlers execute through the supervised Python-hook boundary. Their result is provenance-marked. For compatibility, the shell returns the upstream-visible value. Native proof APIs distinguish a user hook assertion from a kernel theorem unless the hook supplies a verifiable certificate.

## 7. Contradiction policy

Contexts declare one of:

- `RejectOnContradiction`: adding inconsistent facts fails with a witness;
- `Paraconsistent`: contradictory local facts are retained and cannot explode into arbitrary conclusions;
- `CompatibilityProfile`: reproduce the profiled assumptions API while retaining a native contradiction diagnostic.

Classical explosion is forbidden in an inconsistent imported/user context unless an explicit proof mode opts into it. This prevents one bad assumption from proving every identity.

## 8. Domain lattice and domain constructors

Core domains include, at minimum:

### 8.1 Atomic exact domains

- `ZZ`: arbitrary-precision integers;
- `QQ`: normalized arbitrary-precision rationals;
- `GF(p)` and finite extensions where required;
- `ZZ/nZZ` with explicit non-field behavior;
- algebraic number fields `QQ(α)`;
- exact real algebraic numbers;
- Gaussian integers/rationals and other named exact extensions;
- symbolic expression domain `EX` as an explicit escape hatch, not the default for every unknown.

### 8.2 Constructed algebraic domains

- polynomial rings `R[x1, …, xn]` with monomial order;
- Laurent polynomial rings;
- fraction fields;
- quotient rings and ideals;
- algebraic extensions and towers;
- power-series and truncated-series rings;
- matrix rings and modules;
- noncommutative free algebras where supported;
- tensor/index domains;
- Boolean algebras and logic theories.

Every domain constructor has canonical parameters and a stable `DomainId`.

### 8.3 Certified analytic domains

- exact rationals with directed rounding conversion;
- real intervals and balls;
- complex rectangles/discs/balls;
- affine/Taylor models for correlated uncertainty where justified;
- symbolic constants with certified enclosures;
- branch-aware analytic continuations.

Certified numeric domains are not ordinary binary floats with an error estimate attached after the fact.

## 9. Arbitrary-precision substrate

The project needs a pure-Rust, memory-safe arbitrary-precision substrate with no C/C++ FFI. The architectural requirement is independent of the final implementation choice.

### 9.1 Integer requirements

- signed magnitude or equivalent canonical representation;
- small-integer inline optimization;
- schoolbook, Karatsuba, Toom-Cook, and FFT/NTT multiplication selected by measured thresholds;
- exact division, gcd/extended gcd, modular inverse, Jacobi/Legendre symbols;
- Montgomery/Barrett modular arithmetic;
- deterministic prime generation/testing support;
- constant-time variants only where a cryptographic boundary explicitly requires them;
- cancellation checkpoints at bounded algorithmic boundaries;
- coefficient-height accounting;
- portable deterministic serialization.

### 9.2 Rational requirements

- canonical denominator positivity;
- gcd-reduced canonical storage;
- delayed/cross-cancelled arithmetic to control growth;
- exact comparison without overflow;
- rational reconstruction and continued fractions;
- height bounds and budget charging;
- explicit construction of noncanonical transient forms only inside guarded kernels.

`BigRational::metered_to_f64` rounds an exact quotient directly to binary64 using
the caller's cumulative `BudgetMeter`. Scaling, division, remainder comparison
and ties-to-even rounding use the governed integer kernels; large numerator and
denominator values never become an intermediate `infinity / infinity`. The API
preserves signed underflow and reports true overflow as an infinity for its
caller to admit or refuse. Height-only terminal cases avoid coefficient copies,
and all terminal cases check cancellation before returning. The ordinary
`to_f64` conversion keeps its existing arithmetic path and rounding contract.

### 9.3 Floating requirements

Compatibility floats reproduce the selected SymPy/mpmath-facing profile. Native certified floats use explicit precision and rounding mode. The types must be distinct so an uncertified approximation cannot inhabit a certified-ball payload.

## 10. Numeric tower

The semantic numeric tower distinguishes at least:

```text
Integer
Rational
FiniteFieldElement
AlgebraicNumber
RealAlgebraic
ExactConstant
BinaryFloat(profile, precision, payload)
RealBall(precision, midpoint, radius)
ComplexBall(precision, midpoint, radius)
Infinity variants
NaN / indeterminate forms
SymbolicNumber
```

Promotion is a typed coercion decision with a receipt. There is no ambient “convert everything to float” fallback.

### 10.1 Exact constants

Constants such as `pi`, `E`, Euler's constant, Catalan's constant, and zeta values retain symbolic identity. Numeric evaluation produces certified enclosures when native evidence is requested, or profile-compatible floats in ordinary drop-in calls.

### 10.2 Infinities and indeterminate values

Positive/negative infinity, complex infinity, NaN, signed zero, and branch-sensitive limits have explicit representations and operation tables. Compatibility behavior can differ from ordinary extended-real algebra and must be profiled rather than “fixed” by intuition.

## 11. Algebraic numbers

The algebraic-number program includes:

- square-free and irreducible defining polynomials;
- isolating intervals/regions;
- canonical primitive elements and embeddings;
- exact arithmetic with reduction;
- equality and ordering certificates;
- minimal polynomial computation;
- field-tower simplification and primitive-element selection;
- root objects preserving multiplicity and branch/order conventions;
- conversion between radical forms and algebraic representations when certified.

An algebraic number's identity includes its defining data and chosen embedding, not merely a floating approximation.

## 12. Domain inference

Domain inference is an explicit planner returning:

```text
DomainInference
├── selected domain
├── candidate alternatives
├── coercions required
├── evidence/assumptions used
├── lossless/lossy status
├── rejected alternatives and reasons
└── receipt
```

The planner prefers the smallest exact domain supporting the requested operations, subject to compatibility and performance policies.

Examples:

- integer coefficients stay in `ZZ[x]` for primitive/content-aware algorithms;
- rational functions use a fraction field only when required;
- modular images are algorithmic projections with reconstruction obligations, not a permanent domain change;
- symbolic coefficients remain in a generic or tower domain rather than being coerced to floats;
- matrix domains retain element domain and dimensions.

## 13. Coercion graph

Coercions form a versioned directed graph. Each edge declares:

- total or partial;
- injective or lossy;
- exact or approximate;
- cost model;
- required assumptions;
- inverse/reconstruction support;
- evidence emitted;
- profile-visible behavior.

Path selection is deterministic under a fixed policy. Ambiguous or incomparable coercions are refused or returned as alternatives; arbitrary registration order is not semantic policy.

User-defined domains can register coercions only through a capability-scoped plugin interface with conflict detection and conformance tests.

## 14. Branch and analytic policy

Analytic operations carry a branch policy:

- principal complex branches;
- real-restricted branches;
- symbolic multivalued objects;
- local analytic continuation along a path;
- compatibility-profile behavior.

Transformations involving `log`, powers, roots, inverse trigonometric functions, special functions, and contour-sensitive integrals name the branch policy and discharge side conditions.

A rewrite such as `log(x*y) -> log(x) + log(y)` is not globally valid over complex values. It requires domain/assumption proof or remains a conditional transformation.

## 15. Certified numerics

### 15.1 Evidence contract

A certified numerical result includes:

```text
CertifiedValue
├── enclosure
├── precision and rounding policy
├── target term_id
├── assumptions_context_id
├── algorithm/verifier versions
├── singularity/branch analysis
├── termination/error bound certificate
└── receipt
```

The verifier checks enclosure arithmetic and any algorithm-specific certificate. A narrow interval is not automatically valid because an algorithm claims it is.

### 15.2 Adaptive precision

Precision is increased under a typed budget until one of:

- the requested enclosure width is proved;
- a decision predicate is separated from zero/a boundary;
- an exact recognition certificate succeeds;
- the computation is inconclusive;
- cancellation or resource exhaustion occurs.

No fixed “extra digits” heuristic is presented as a correctness guarantee.

### 15.3 Exact recognition

Integer-relation, rational reconstruction, or algebraic recognition may propose exact forms from high-precision values. Acceptance requires an independent exact or certified check. Recognition confidence alone is `HeuristicCandidate`.

### 15.4 Implemented bounded numerical APIs

`nsolve_certified` and a compiled residual system's `solve_certified` method
connect finite-real Newton candidate generation to the independent original-source
root checker. One captured program and typed assumption snapshot govern both
phases. A binary64 candidate proposes exact rational centers and boxes; only
whole-box C1 checks, strict Krawczyk inclusion and a contraction bound authorize
the immutable `RootBoxReceipt`. The claim is one unique nonsingular root in the
declared box. It does not establish global completeness. The search admits square
systems with 1 through 16 variables, uses at most 24 certificate attempts, and
escalates interval precision only within 8 through 128 decimal digits.

Both entry points accept an explicit candidate `backend`: `"python"` retains
the existing scaled QR/Newton generator; `"frankennumpy"` and `"frankenscipy"`
select the real pinned consumers described in section 15.8. Backend choice does
not change the root claim or its verifier. Exact-source, shape, captured
assumptions and certificate-search policy are admitted before a donor executes.
Only its approximate coordinates enter the existing box search; a donor's
convergence flag, diagnostics or claimed evidence cannot authorize a receipt.

`certified_integral` encloses a proper real integral over finite rational limits
without requiring an antiderivative. The calculus generator proposes a partition;
the independent core checker recomputes every cell's original-source function and
derivative bounds, verifies complete coverage, and checks the final exact width.
Its centered C1 bound includes point-evaluation rounding and is intersected with
the whole-cell range bound. `tolerance` bounds the complete enclosure width, so
the returned midpoint's error is at most half that tolerance. Precision is 8
through 128 digits and the partition has at most 1024 intervals. Reversed limits
negate the enclosure. Equal limits still require a defined, admitted original
source. Original poles, nonsmooth endpoints, improper integrals and principal
values remain explicit refusals.

```python
from sympy import Rational, Symbol, certified_integral, exp, nsolve_certified

x, y = Symbol("x"), Symbol("y")
root = nsolve_certified([x*x + y*y - 5, x - y - 1], [x, y], [2, 1])
integral = certified_integral(
    exp(-x*x), (x, 0, 1), tolerance=Rational(1, 10000),
)
```

These APIs accept exact source literals for certification and expose native-derived
immutable statements and bounds. Unsupported custom objects, inconsistent captured
assumptions and exhausted work cannot yield accepted receipts. Ordinary `nsolve`
remains an approximate API. These bounded synchronous implementations do not close
the full runtime, compatibility-profile or end-to-end campaign gates.

### 15.5 Checked residual-program persistence

A compiled residual system exposes `to_bytes()`. The public
`load_residual_system(data, *, residuals, args)` loader accepts the existing
versioned native JSON format, bounded to 16 MiB. Import independently replays
the retained derivative proofs, omitted-zero checks, sparsity and bytecode
provenance before comparing the caller's exact original residuals and ordered
typed variables. It also reapplies the Python bridge's input and operation caps.

```python
from pathlib import Path
from sympy import Symbol, compile_residual_system, load_residual_system

x = Symbol("x", positive=True)
source = [x*x - 2]
program = compile_residual_system(source, [x])
Path("checked-system.json").write_bytes(program.to_bytes())

restored = load_residual_system(
    Path("checked-system.json").read_bytes(), residuals=source, args=[x],
)
assert restored.residuals(2) == [2.0]
```

The caller supplies the expected source and argument declarations, including in
a fresh process. The loader never invents assumptions from an identity digest or
remaps Dummy identities. Caller objects provide the argument layout, assumption
snapshot and floating-source guard. A floating residual remains approximate-only
when reloaded against floating expected source; explicitly declaring the matching
exact Rational source is a new source declaration.

Python objects, argument nesting, evaluation budgets, root receipts and trusted
verification flags are not serialized. Encoding and proof replay release the GIL
but remain bounded admission work outside `EvaluationBudget`. After import,
evaluation, batches, enclosures and certified root search use the same numerical
interfaces and cumulative budgets as a freshly compiled system.

### 15.6 Shared numerical budgets and cancellation

Native scalar compilation also accepts one cumulative caller ledger.
`CompiledExpr::try_compile_with_meter` generates candidate bytecode;
`compiled_expression_matches_with_meter` independently checks the original
typed source against that program. `try_compile_checked_with_meter` performs
both phases on the same ledger and returns the program only after its final
cancellation checkpoint. Fuel spent generating a candidate is not reset when
checking begins. An exhausted or cancelled checker publishes no program.

These entry points charge recursive visits and edges, instruction emission,
actual requested operation-buffer growth, final bytecode validation, bounded
name handling and exact rational-to-binary64 conversion. The checker meters
both its source preflight and independent source/opcode traversal. Identifier
names are capped at 4096 UTF-8 bytes, and refusal diagnostics never render
unbounded expression trees or bigint decimal strings. Memory counters count
cumulative requested payloads; standard-library allocation and lookup remain
cooperative boundaries. They do not establish a wall-time interruption bound.

```rust
use fsym_budget::{Budget, BudgetLimits};
use fsym_calculus::compile::CompiledExpr;
use fsym_core::{Symbol, parse};
use std::collections::HashMap;

let source = parse("x^2 + 1").unwrap();
let variables = HashMap::from([(Symbol::new("x"), 0)]);
let mut ledger = Budget::new(BudgetLimits::uniform(1_000_000, 0));
let program =
    CompiledExpr::try_compile_checked_with_meter(&source, &variables, &mut ledger)
        .unwrap();
assert_eq!(program.try_eval_finite_with_meter(&[3.0], &mut ledger).unwrap(), 10.0);
```

The governed scalar APIs begin with an already constructed immutable native
expression and variable map. They do not govern Python source extraction,
symbolic differentiation, Jacobian/Hessian construction or proof replay.
The Python `compile_numeric` constructor retains its existing separate
admission contract; its callable's numerical `budget=` does not meter construction.
Checked binary64 lowering does not certify rounding error or numerical roots.

Python compilation for the native numerical engine reads retained built-in argument slots and
bounded native syntax directly. Native-only scalar trees and matrix storage
receive borrowed whole-source preflight before child/cell copies. They do not
reconstruct Python classes from function names. Unsupported custom nodes and
unknown native function tags refuse without running their constructors, argument
properties or setters. Only the existing built-in source-tag mapping is
normalized; unregistered alias tags remain unsupported.
This admission path is shared by scalar, residual and objective compilation and
the expected-source check when loading a residual program.
The separate `lambdify(..., modules="math")` source interpreter is outside this
native admission contract.

Matrix sources use captured retained cells when present, or bounded native cell
snapshots when no Python surface survives. Typed native symbol identities remain
intact. Float-origin syntax remains marked inexact even when its binary64 value
is represented by an exact rational during lowering, so it cannot enter exact
source certification. These source-admission bounds remain separate from the
evaluation ledger and do not promise full compatibility for opaque arithmetic.

Compiled binary64 evaluation accepts a caller-owned cumulative ledger. Native
`CompiledExpr::try_eval_with_meter` retains ordinary IEEE evaluation;
`try_eval_finite_with_meter` rejects nonfinite inputs and intermediate values.
Dense residual/Jacobian methods, sparse Jacobian methods, and checked objective
and Hessian-product methods also expose `*_with_meter` variants. The same
`BudgetMeter` passes through every expression, derivative stage and output copy.
A runtime caller can pass its existing `FsymCx` to observe owning-region
cancellation without giving numerical work access to the protected verifier pool.

```rust
use fsym_budget::{Budget, BudgetLimits};
use fsym_calculus::compile::CompiledExpr;
use fsym_core::{Symbol, parse};
use std::collections::HashMap;

let variables = HashMap::from([(Symbol::new("x"), 0)]);
let program = CompiledExpr::try_compile(&parse("x^2 + 1").unwrap(), &variables).unwrap();
let mut ledger = Budget::new(BudgetLimits::uniform(1_000_000, 0));
assert_eq!(program.try_eval_finite_with_meter(&[3.0], &mut ledger).unwrap(), 10.0);
```

The Python preview exposes `EvaluationBudget`, `EvaluationBudgetExceeded` and
`EvaluationCancelled` from `sympy`. Pass `budget=` to a `compile_numeric` callable,
compiled residual evaluation, checked objective evaluation or ordinary `nsolve`.
Residual `enclose`, `certify_root_box` and `solve_certified` methods, and
`nsolve_certified`, also accept the same budget.
The same object covers repeated calls, batch rows, derivative stages and supported
solver iterations, including rejected line-search trials, exact preconditioner
proposals and interval/root-verification retries. Precision escalation and box
changes never reset it. Consumed work remains spent after an exception. Omitting
`budget` retains the existing bounded API without a cumulative caller ledger;
each native certification call retains its fixed safety envelope.

```python
from sympy import (
    EvaluationBudget, Symbol, compile_numeric, compile_objective,
    compile_residual_system, nsolve,
)

x = Symbol("x")
budget = EvaluationBudget(
    max_steps=100_000, max_memory_bytes=1_048_576, max_allocations=1024,
)
f = compile_numeric(x, x*x + 1)
assert f(3, budget=budget) == 10.0
assert f.evaluate_batch([(1,), (2,), (3,)], budget=budget) == [2.0, 5.0, 10.0]
system = compile_residual_system([x*x - 2], [x])
residuals, jacobian = system.evaluate(1.5, budget=budget)
objective = compile_objective((x - 2)**2, [x])
value, gradient, hessian = objective.evaluate(3, budget=budget)
root = nsolve(x*x - 2, x, 1.5, budget=budget)
remaining = budget.remaining_steps
budget.cancel()  # Irreversible; subsequent uses raise EvaluationCancelled.
```

The same ledger can span approximate search and independent acceptance:

```python
from sympy import EvaluationBudget, Symbol, compile_residual_system

x = Symbol("x")
system = compile_residual_system([x*x - 2], [x])
budget = EvaluationBudget(max_steps=10_000_000, max_memory_bytes=512 * 1024 * 1024)
receipt = system.solve_certified(1.5, budget=budget)
assert receipt.claim == "one unique nonsingular real root in the declared closed box"
```

The interval checker currently reserves 64 MiB of cumulative memory allowance
per call before entering its bounded ball arithmetic. Automatic preconditioning
first requests a point-Jacobian enclosure, then invokes the root checker, so a
trial typically includes two such reservations. These are conservative work
allowances, not measured allocations or RSS. The default 256 MiB budget does not
promise enough fuel for every requested retry. Callers can supply a larger
cumulative allowance; a refused trial never creates a fresh ledger.

`evaluate_batch` is available for compiled numerical callables and residual
systems. It admits at most 4096 rows; row count times the larger flattened input
or output width is at most 262144, counting an empty width as one. A later row
failure publishes no earlier rows. Native caller-owned output buffers likewise
remain unchanged on cancellation, exhaustion or evaluation failure. Budget
exhaustion and cancellation remain distinct typed operational outcomes; solver
backtracking does not reinterpret them as domain errors.

Fuel counts deterministic logical instruction, reduction, validation and
publication work. Memory and allocation counters accumulate requested native
input snapshots and scratch/output buffers, with conservative reservations for
interval kernels and bounded exact-input arithmetic. The Python bridge charges native
input snapshots while holding the GIL, before arithmetic runs without it. These
counters do not measure RSS, allocator overhead or peak live memory, and releasing
a temporary does not refund them. Python argument-layout handling and CPython
object/result-container allocation are outside this evaluation ledger.
Compilation and symbolic proof admission/replay remain separate phases outside
it, with their own existing admission rules. Certified quadrature and other
exact symbolic APIs retain their separate resource contracts. Exact rational
root-witness preparation charges logical, limb-weighted work before arithmetic.
A budgeted scalar `nsolve` uses the admitted native finite-real compiler
and refuses functions outside that compiler's supported subset.

Caller exhaustion, intrinsic interval-work limits and cancellation propagate as
`EvaluationBudgetExceeded` or `EvaluationCancelled`, both derived from
`RuntimeError`. They cannot be consumed by the root search's mathematical
`ValueError` retry path. A fallible native buffer allocation that fails outside
the ledger raises `MemoryError`, which also stops retries. Candidate generation,
exact inversion, native checking
and final receipt assembly all check the same cancellation state. A failed or
cancelled operation publishes no accepted receipt.

Cancellation is cooperative at numerical safe points and before publication.
The synchronous Python bridge releases the GIL during native arithmetic, permits
another caller to request cancellation, and creates no native worker. A ledger
cannot be borrowed by two concurrent evaluations; independent concurrent requests
need independent ledgers. This does not promise a universal wall-time interruption
bound or metering of arbitrary Python callbacks.

Exact integer and rational literals use direct native conversion. Rational
quotients are rounded once even when their coprime components individually exceed
binary64's finite range. True final overflow refuses; finite underflow uses the
bytecode's canonical positive zero. Evaluation remains approximate binary64
arithmetic: budgeting and checked symbolic derivatives do not certify numerical
enclosures, roots or convexity, or close the end-to-end campaign/profile gates.

### 15.7 Explicit numerical callbacks in native expressions

`compile_numeric_hybrid(args, expression, *, callbacks)` connects bounded native
binary64 fragments to explicitly registered Python numerical functions. The
mapping uses actual custom `Function` classes as keys and captures the supplied
callable objects when compiling. It never discovers `_imp_` hooks, resolves
custom classes by a printed name, or silently replaces a built-in function.

```python
from sympy import (
    Add, EvaluationBudget, Function, Pow, Symbol, compile_numeric_hybrid,
)

class Response(Function):
    nargs = 1

x = Symbol("x")
calls = []

def response(value):
    calls.append(value)
    return value + 1

source = Add(Pow(Response(x), 2, evaluate=False), x, evaluate=False)
program = compile_numeric_hybrid(x, source, callbacks={Response: response})
budget = EvaluationBudget(max_steps=100_000)
assert program(2, budget=budget) == 11.0
assert program.evaluate_batch([(0,), (1,)], budget=budget) == [1.0, 5.0]
assert calls == [2.0, 0.0, 1.0]
assert program.evidence == "approximate_with_user_callbacks"
```

Use retained surface expressions, including held `Add`, `Mul` and `Pow`, when
combining custom functions. Canonical native-only storage can lose the exact
Python class of a custom function; such a source is refused instead of guessing
from its name. Held powers retain their original operand objects. Compilation
reads the base classes' stored argument slots without calling custom argument
properties or printers. Native-only sources receive a borrowed preflight before
their child expressions are cloned. Source and callback-mapping snapshots remain
fixed after construction; mutating the caller's mapping or matrix does not alter
the compiled occurrence graph. Captured callables may still have mutable state.

Every explicit callback occurrence executes independently, including repeated
references to the same object with equal arguments. Native subexpressions and
callbacks execute in stored child/output order. A native domain failure prevents
later occurrences from running; earlier completed effects remain observable.
Literal power exponents stay part of the native syntax, preserving the supported
negative-base integer-power behavior and the positive-base guard for dynamic
real exponents. Callback outputs must be exact built-in `int`, `float` or `bool`
values that convert to finite binary64; arbitrary `__float__` hooks are refused.

Each call or complete batch uses one `SupervisedCallbackSession`, supplied with
`session=`, inherited from an active request, or created for that evaluation.
Invocation counts and nested native work accumulate in that session. Individual
callbacks retain the input, reentrancy and post-return wall-time caps. Callbacks
that fail, return invalid values, or observe cancellation taint their owning
session; caught nested supervision failures cannot publish an outer result.
There is no automatic retry or rollback of arbitrary Python effects.

One optional `EvaluationBudget` covers native fragment evaluation and logical
hybrid dispatch. Reentrant hybrid calls inherit the active ledger when omitted,
and a different explicitly supplied ledger or owning session is refused. The
ledger does not meter arbitrary callback internals, compilation or CPython object
allocation. Cancellation is checked before callbacks, during native evaluation,
after callback return and before publication; Python code remains in process
without a forced interruption deadline. A later batch failure returns no partial
row list while preserving effects that have already occurred.

The graph admits at most 4096 actions, 65536 native instructions, 128 registered
callback classes, and 256 children per mixed operator or callback, in addition to
the ordinary numerical source, variable, literal and batch caps. Scalar and
nested list/tuple output shapes are preserved; matrices produce nested lists.
`variables`, `callback_slots`, `operation_count` and `native_fragment_count`
expose the captured structure. These programs have no pickle or portable-program
transport, derivative certificate, interval enclosure or root-receipt interface.
The explicit callback mapping is a user assertion, and all hybrid results remain
approximate. This API does not close the campaign or compatibility-profile gate.

### 15.8 Real numerical consumers from Python

A checked `compile_residual_system` program, including a source-checked loaded
program, exposes `solve_candidate(initial, *, backend="frankennumpy", tol=None,
maxiter=None, max_step_norm=None, budget=None)`. It calls the real pinned
FrankenNumPy or FrankenSciPy consumer through the native bridge. The initial
point is a flat finite-real vector in `program.variables` order, or a scalar for
one variable. This interface admits square systems with 1 through 16 variables.

```python
from sympy import EvaluationBudget, NumericRootCandidate, symbols, compile_residual_system

x, y = symbols("x y")
system = compile_residual_system([x*x + y*y - 5, x - y - 1], (x, y))
budget = EvaluationBudget(max_steps=1_000_000)
candidate = system.solve_candidate([1.8, 0.8], backend="frankennumpy", budget=budget)
assert isinstance(candidate, NumericRootCandidate)
assert candidate.variables == (x, y)
assert candidate.residual_norm <= 1e-12
assert candidate.evidence == "approximate"
other = system.solve_candidate([1.8, 0.8], backend="frankenscipy", budget=budget)
assert other.residual_norm <= 1e-10
receipt = system.solve_certified([1.8, 0.8], backend="frankenscipy")
```

`frankennumpy` evaluates the checked symbolic Jacobian and calls the pinned
dense linear solver. Its defaults are tolerance `1e-12`, 64 iterations and
maximum step norm `1e6`; it accepts 0 through 1024 iterations. Zero iterations
only tests the initial point. `frankenscipy` calls the pinned `fsolve` with a
finite-difference Jacobian, a fixed 200-iteration cap and residual tolerance
`1e-10`. Supplying any non-`None` tolerance, iteration or maximum-step override
to that backend is refused. Backends are selected explicitly and never silently
fall back to another solver.

The immutable result holds `root` as a tuple of binary64 coordinates,
`variables` as the captured original caller objects, `residual_norm` as the
re-evaluated infinity norm of the original residuals, `iterations`, `backend`
and `evidence`. Approximate candidates can include a singular root or violate a
variable's declared assumptions. None of these fields grants a root certificate.
Use the separate certified-search API for an independently checked local claim.

`system.solve_certified` and `nsolve_certified` accept the same donor backend
names, plus the default `"python"` backend. `tol=None` and `maxiter=None`
select that backend's defaults; Python retains its effective tolerance `1e-12`
and 200-iteration limit. Python refuses `max_step_norm`, and SciPy refuses all
explicit non-`None` solver-control overrides. Every candidate passes through
the same original-source interval checker and captured-assumption checks.
One supplied ledger spans donor work, exact inverse proposals, rejected boxes,
precision escalation and receipt publication. Operational failures propagate
without becoming mathematical retries. Unsupported exact source or assumptions
refuse before candidate work; singular/no-root cases cannot gain a receipt just
because an approximate solve returned a small residual.

One supplied `EvaluationBudget` covers input snapshots, native buffers, source
evaluations and conservative donor work through final candidate publication.
Failure retains consumed resources; cancellation, exhaustion and allocation
errors keep their operational types. Donor contract violations are operational
errors, not mathematical no-root results. Execution releases the Python
interpreter, creates no worker and checks cancellation between synchronous
kernels; it does not promise a forced wall-time interruption. Compilation and
Python container allocation retain their separate accounting limits. This
interface does not close the end-to-end consumer, campaign or profile gates.

### 15.9 Solving residual systems with explicit callbacks

`compile_hybrid_residual_system(residuals, args, *, jacobian, callbacks)`
captures one ordered graph containing both the residual vector and an explicit
Jacobian. Custom numerical functions use the same exact-class mapping and
supervised occurrence semantics as `compile_numeric_hybrid`. The required
Jacobian is a caller assertion: compilation does not call derivative hooks or
prove that the supplied entries differentiate the residuals.

```python
from sympy import Eq, EvaluationBudget, Function, Symbol, compile_hybrid_residual_system

class Response(Function):
    nargs = 1

class ResponseSlope(Function):
    nargs = 1

x = Symbol("x")
system = compile_hybrid_residual_system(
    [Eq(Response(x), 2, evaluate=False)], (x,),
    jacobian=[[ResponseSlope(x)]],
    callbacks={Response: lambda value: value*value,
               ResponseSlope: lambda value: 2*value},
)
assert system.evaluate(2) == ([2.0], [[4.0]])
root = system.solve(1.5, budget=EvaluationBudget(max_steps=100_000))
assert abs(float(root[0]) - 2**0.5) < 1e-10
assert system.evidence == "approximate_with_user_callbacks"
assert system.jacobian_evidence == "user_supplied"
```

`evaluate` returns the residual vector and dense Jacobian together;
`evaluate_batch` returns complete pairs under one session and ledger. The
`residuals` view executes only the original residual prefix. The `jacobian`
view first executes the original residuals, so an asserted derivative cannot
erase a source domain check or an observable callback occurrence. Source
containers, callback mappings, variable objects and occurrence order are
captured once; later container mutation does not change the program.

Constructed equations retain their original left and right operand objects.
The compiler reads that stored pair directly, preserving exact custom function
classes and left-before-right occurrence order without invoking operand
properties, constructors, printers or setters. Each equation becomes the held
residual `lhs - rhs`. A missing custom callback binding refuses even when the
custom class shares a built-in function's name. For equations recovered from
native-only storage, arithmetic and atomic sides remain supported after a
bounded preflight; function-bearing sides refuse because their original Python
class provenance is unavailable. Supply an equation built from the actual
operand objects to retain that provenance.
The general `nsolve` and `nsolve_certified` equation adapter requires that
retained operand pair and refuses a native-only Eq before lifting any child.
Pass an Eq constructed from actual Python operands, or supply residual
expressions directly.

`solve(initial, *, tol=1e-12, maxiter=200, budget=None, session=None)` returns
an approximate column Matrix. It reuses ordinary system `nsolve`'s equilibrated,
column-pivoted QR iteration for square and overdetermined systems. Initial
coordinates are flat, even when evaluation arguments have a nested layout.
An exact-zero binary64 residual can terminate before derivative evaluation;
this remains an approximate observation and supplies no mathematical evidence.

One owning callback session and optional cumulative budget cover all iterations,
native fragments, dense work, line-search trials and final publication. Nested
hybrid requests inherit both scopes and cannot substitute a new ledger or
session. Every callback occurrence executes afresh. Line search may reject a
native domain failure only when no callback ran in that trial and the request
remains healthy. Callback exceptions, invalid callback results, failures after
an effect, cancellation and resource exhaustion propagate without automatic
retry. Already completed effects cannot be undone; a failed solve or batch
publishes no partial numerical result.

The source admits at most 64 variables, 256 residuals and 4096 Jacobian entries,
subject to the existing combined output, action and instruction limits. Solves
require at least as many residuals as variables and retain the shared bounded
iteration, evaluation and dense-work limits. Python callback internals,
compilation and Python object allocation remain outside native accounting, and
non-cooperative callbacks have no forced cancellation deadline. These programs
expose no checked native residual system, portable/pickle transport, derivative
proof, interval enclosure or root-certificate interface. Use held custom
expressions to retain the Python class identity required by the callback lane.

## Original-source objective and stationary-point certificates

The bounded native `fsym_core::enclose_objective` and
`metered_enclose_objective` APIs evaluate one original typed expression over a
closed real coordinate box. Their private-field `ObjectiveEnclosure` binds the
source, ordered symbol identities, box and precision to objective, gradient
and dense Hessian enclosures. Second-order interval automatic differentiation
uses no symbolic differentiation generator, compiled derivative or sampled
derivative. The product and composition rules retain both mixed terms and the
inner Hessian. This establishes C2 bounds on the admitted original expression;
it does not establish stationarity, convexity or a global optimum.

`certify_stationary_point` and the caller-metered `verify_stationary_point`
accept a `RootBoxWitness` as an untrusted proposed box, center and rational
preconditioner. They independently evaluate the original objective twice,
then apply strict Krawczyk interior inclusion and an exact contraction bound
to its gradient and Hessian. An accepted `StationaryPointReceipt` establishes
one unique nonsingular stationary point in the specified box. Its stationary
enclosure is strictly inside that box. Its objective-value enclosure covers
the entire supplied box and therefore the stationary value; tightness is not
claimed.

Interval LDL checks the Hessian inertia over the whole box. It can classify a
strict local minimum, strict local maximum or saddle. A pivot interval
containing zero produces `Unclassified`, preserving the independently proved
stationary-point statement without asserting any extremum. No-pivot LDL is
incomplete, including for some nonsingular indefinite matrices. A failed
Krawczyk check produces no stationary-point receipt at all. These APIs do not
search for a point and do not claim global optimality outside the box.

The lane supports 1..16 variables, 8..128 decimal digits and the existing
root-box depth, node, coefficient-height, arithmetic and cumulative-allocation
caps. Arithmetic, integer powers from -64 through 64, positive-real dynamic
powers, sin, cos, exp, log/ln, sqrt, atan, tan and hyperbolic functions have
explicit C2 interval rules. Logarithms, square roots and noninteger powers
require strictly positive arguments throughout the complete box. Poles and
all original children remain visible even behind zero factors or held zero
powers. Unsupported functions, unbound typed symbols, invalid inputs,
resource exhaustion and cancellation refuse explicitly.

A single caller-owned `BudgetMeter` covers both derivative orders, all
stationary-point phases and receipt publication. Charges remain consumed on
failure; these APIs do not charge a protected verifier pool through a plain
`Budget`. This is synchronous cooperative execution, not a claim of runtime
supervision or forced cancellation inside arbitrary foreign calls. The new
regressions are `objective_enclosure`, `stationary_certificate` and the
existing `root_box_general` suite. Their execution status is reported by CI;
the campaign, full compatibility profile and workstream gates remain open.


## Exact rational monotonicity

The public increasing/decreasing predicates admit bounded univariate rational

all original source-domain exclusions before differentiating, replay the

independently checked complete rational sign chart. Endpoint comparisons are
exact for rational and real `CRootOf` values; no sampled or binary64 sign

Strict directional predicates use the pinned SymPy 1.14 pointwise derivative

existing `is_monotonic` convention remains weak increasing OR decreasing;
this is an existing profile discrepancy, not a newly asserted upstream

## Python objective certification

The existing `compile_objective(objective, args)` callable now exposes
`enclose(box, precision=32, budget=None)` and
`certify_stationary_point(box, center=None, preconditioner=None, precision=32,
budget=None)`. A box is an exact built-in list or tuple of exact rational
endpoint pairs, ordered by the compiled variables. Integers, shell rationals
and `fractions.Fraction` are admitted; floats and custom conversion hooks are
not. Source Float literals continue to support approximate evaluation but
refuse certification. Compilation snapshots the symbol assumptions bound to
the native source, and certification checks the entire box against that
snapshot.

For example:

```python
from sympy import symbols, compile_objective

x, y = symbols("x y")
objective = compile_objective((x - 1)**2 + 2*(y + 2)**2, (x, y))
bounds = objective.enclose([(0, 2), (-3, -1)])
point = objective.certify_stationary_point([(0, 2), (-3, -1)])
assert point.kind == "strict_minimum"
assert point.stationary_enclosure == ((1, 1), (-2, -2))
```

`ObjectiveEnclosure` returns exact endpoint pairs for `value`, `gradient`
and `hessian`. `StationaryPointReceipt` exposes the accepted box, center,
preconditioner, stationary enclosure, whole-box objective/gradient/Hessian
enclosures, contraction bound and local classification. Both bind the original
objective and immutable native symbol handles; neither has an unchecked
native constructor. Receipt adapters are immutable.

When center and preconditioner are omitted, the shell proposes the box
midpoint and an exact rational inverse of a midpoint Hessian enclosure.
This bounded proposal has no acceptance authority: the core checker still
recomputes the original source over the complete box. An unsupported or
singular proposal, an inconclusive interval check, exhausted resources or
cancellation returns no stationary-point receipt. A caller may supply a
different exact center and preconditioner without changing the acceptance
criteria.

A reusable `EvaluationBudget` covers exact proposal arithmetic, native
buffers, verification and the final publication checkpoint cumulatively.
Compilation and CPython object allocation remain outside that ledger, as in
the existing numerical API. The public regressions live in
`python/tests/test_certified_objective.py`; CI loads the actual checked-out
native extension before running them. This adds a bounded objective lane to
the active Jacobian campaign, without claiming a global optimizer or closing
the broad calculus, solver or compatibility workstreams.


## Bound-root identities inside expressions

An exact `CRootOf` binds its polynomial generator. Renaming that generator

index. Parent expressions now retain this identity for equality and hashing,
including square roots, quotients, held arithmetic and admitted function
applications. This repairs the singular-value comparison failures caused by
internal eigenvalue generator names and makes equal composites usable as
dictionary/set keys and whole-expression substitution targets.

The bounded key preserves the ordered enclosing expression shape, every
typed free-symbol payload and the actual Python function class. It does not
sort held operands, simplify zero/unit factors, or establish general algebraic
equivalence between different defining polynomials. Genuine native arithmetic
variants cannot be impersonated by functions with matching names. Piecewise
branch tuples and relational/logical conditions are interpreted only through
their exact built-in owner; same-named user classes cannot capture them.

The implementation reads retained slots without executing user getters,

## Original-source global extrema on a finite box

The native `certify_box_extremum` and metered `verify_box_extremum` APIs check
an exact rational candidate point against a declared closed rational box.
Unlike the local stationary-point checker, this claim permits an optimizer
on a boundary face and can admit singular Hessians. It proves a global
minimum or maximum **on that box**, with no assertion outside it.

The independent core evaluator first establishes the original objective's
C2 domain and encloses its Hessian on the complete box. A sufficient interval
LDL test establishes positive semidefiniteness for a minimum or negative
semidefiniteness for a maximum. A pivot that reaches zero is accepted only
when its entire remaining Schur column is exactly zero. A zero diagonal with
a nonzero coupling never becomes evidence of convexity.

The checker recomputes the original gradient at the exact candidate point.
For a minimum, each interior gradient must be exactly zero; lower-face
gradients must be nonnegative and upper-face gradients nonpositive. The
signs reverse for a maximum. Fixed coordinates impose no directional
condition. Convexity/concavity and these first-order inequalities establish
the global box claim. Candidate derivatives and numerical samples are never
proof inputs.

The immutable receipt binds the source, typed coordinate order, complete
box, exact point, precision, optimum-value enclosure, point gradient and
whole-box Hessian. `uniqueness_proved` is true only when a definite Hessian or
a strictly supporting gradient on every movable coordinate proves it.
False means uniqueness is unproved, rather than asserting multiple extrema.
Flat convex objectives and zero-reaching diagonal curvature can therefore
receive an extremum receipt without an invented uniqueness claim.

The same intrinsic 1..16-dimensional, 8..128-digit, source-depth and rational
size limits apply. One caller-owned ledger covers source admission, both
interval evaluations, curvature checks and publication. Errors retain consumed
work; cancellation returns no receipt. This is a sufficient bounded checker,
so an inconclusive curvature or first-order test refuses even when a true
optimum may exist. It is not a general nonconvex optimizer or a profile gate.

`crates/fsym-core/tests/box_extremum.rs` contains thirteen regression tests,
including a 125-case independent two-dimensional principal-minor criterion,
boundary direction mutations, degenerate curvature, hidden source holes,

## Automatic certified stationary-point search

A compiled objective now offers
`solve_stationary_certified(initial, tol=1e-12, maxiter=200, precision=32,
max_attempts=12, budget=None)`. The initial guess is a flat vector in the
compiled variable order, or a scalar for one variable. The existing bounded
QR/Newton kernel solves the gradient residual using the same immutable
native objective's checked gradient and Hessian, with original-value and
derivative domain checks on every accepted or rejected trial. It does not
differentiate or compile a second objective during the search.

Floating convergence proposes a point only. The shell converts that candidate

precision, and submits each proposal to the original-source stationary-point
checker. Only its immutable accepted receipt can escape. A small floating
residual, a claimed numerical root, or an apparent positive Hessian never
substitutes for the exact inclusion, contraction and curvature obligations.

strict maximum, saddle and unclassified stationary point. This method is not
a global minimizer and does not prove that other stationary points are absent.

exception types, with cumulative work preserved. A native unsupported

certificate trial; it cannot produce accepted evidence or unbounded retries.

typed assumption snapshot, 8..128 starting precision digits, 1..24 total
certificate attempts and 1..10,000 Newton iterations before candidate work.

## Python box-extremum certificates

## Exact rational domains, ranges and extrema

The public `continuous_domain`, `function_range`, `minimum` and `maximum`
utilities now share a bounded exact rational-function analysis. This extends
the earlier complete monotonicity lane to images and extrema. The input is a
rational expression over QQ in one typed real coordinate, restricted to a
connected real interval with exact rational or real indexed-root endpoints.
Empty and singleton domains are admitted too. Other source or domain forms
refuse explicitly.

The complete checked original-source sign chart determines the admitted
domain before any numerator/denominator arithmetic. Held zero products,
zeroth powers and removable denominator factors cannot restore excluded
points. Each remaining continuous component is analyzed using the checked
derivative's complete root chart, exact one-sided endpoint limits and every
interior critical value. Finite algebraic values and all endpoint comparisons
use the existing exact native algebraic evaluator. No floating approximation,
string reconstruction or sampled value can establish an image boundary.

The returned set preserves open and closed image endpoints, singleton images,
infinities and disconnected unions. Equal limiting values become closed when
another included endpoint or critical point actually attains them; a constant
on a nonempty open component still has a singleton image. Rational poles are
handled by exact orders of vanishing and side-dependent signs. Images of
different components merge only when their exact values and endpoint topology
allow it.

For example:

```python
from sympy import Interval, Rational, S, Union, function_range, minimum, oo, symbols

x = symbols("x")
assert function_range(x**2, x, S.Reals) == Interval(0, oo)
assert function_range(1/x, x, S.Reals) == Union(
    Interval.open(-oo, 0), Interval.open(0, oo)
)
assert function_range((x**2 - 1)/(x**2 - 4), x, S.Reals) == Union(
    Interval(-oo, Rational(1, 4)), Interval.open(1, oo)
)
assert minimum(x**4 - 3*x**2, x) == Rational(-9, 4)
```

As in the pinned upstream convention, `minimum` and `maximum` return the
infimum and supremum, including an unattained finite endpoint or infinity.
An empty admitted image raises ValueError for these extrema APIs. The
separate compiled-objective box receipt proves attainment at an explicitly
supplied point; these compatibility helpers do not issue that receipt.

Admission checks the original built-in arithmetic, numeric-atom and symbol
implementations before reading source or endpoint properties. Indexed roots
retain the existing closed-class check. Generated set endpoints are lowered
as typed native values, bypassing the public Interval constructor's textual
infinity compatibility. Changed accessors, identity methods or conversion
hooks cannot silently bind the analysis to different coefficients or bounds.

The Python analysis has intrinsic shared bounds: degree/exponent 128,
32,768-bit intermediate coefficients, four million weighted arithmetic
operations and 16,384 comparisons, alongside the existing source-node/depth
limits. Native chart, differentiation and algebraic checks retain their own
bounded generator/verifier meters; this helper does not claim one shared
caller EvaluationBudget. Exhausted or unsupported exact decisions return
NotImplementedError, with no approximate fallback.
